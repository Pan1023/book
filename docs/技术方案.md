### 2.1 服务拆分原则

- **API 服务**：面向前端的 REST 服务，只做编排与读写，不承载耗时任务；
- **Worker 服务**：与 API 同代码库不同进程，消费队列执行发送、拉信、批量入库、评分计算等耗时操作，可独立水平扩容；
- **追踪服务**：像素回传与链接 302 跳转为独立轻量端点，无鉴权、无同步 DB 写入，可独立部署以应对高并发打开事件。

## 3. 前端技术方案

### 3.1 工程结构

采用 pnpm workspace monorepo，前后端 + 共享类型包同仓：

```
email-center/
├── apps/
│   ├── web/                # Vue 3 前端
│   ├── api/                # NestJS API 服务
│   └── worker/             # 异步任务 Worker
├── packages/
│   └── shared/             # 共享类型 / DTO / 常量（TS）
├── pnpm-workspace.yaml
└── turbo.json
```

### 3.2 关键选型说明

| 项 | 方案 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3 + `<script setup>` + TS | 收件箱、会话、看板均为重数据流页面，组合式 API 便于逻辑复用；与后端共享类型 |
| 组件库 | Element Plus | 表格（大数据量收件人明细）、表单、上传组件成熟，支持响应式与国际化 |
| 图表 | ECharts | 漏斗图、趋势折线、任务对比柱状图开箱即用，满足 3.8 看板需求 |
| 富文本 | TinyMCE | 支持模板插入、图片、HTML 导出（发送需要 HTML 正文）；备选更轻量的 WangEditor |
| 状态管理 | Pinia | 官方标准，TS 支持好 |
| 数据请求 | Axios + 统一封装 | 拦截器统一处理鉴权、错误码、加载态 |
| 实时刷新 | SSE（Server-Sent Events） | 任务发送进度实时推送；单向场景比 WebSocket 简单可靠，断线自动重连 |

### 3.3 响应式与适配

- 布局断点：桌面（≥1200px）双栏/三栏，平板（768–1200px）折叠侧栏，移动端仅保证浏览与基础操作；
- 表格在小屏横向滚动，看板图表容器自适应 resize。

## 4. 后端技术方案

### 4.1 模块划分（NestJS Module）

| 模块 | 职责 | 对应产品功能 |
| --- | --- | --- |
| AccountModule | 邮箱绑定、SMTP/IMAP 配置、连接检测、凭据加密 | 3.1 |
| MailModule | 单发邮件、IMAP 收信、会话聚合、统一收件箱 | 3.2–3.4 |
| CampaignModule | 批量任务 CRUD、收件人导入、调度、暂停/复制/重发 | 3.5 |
| TrackingModule | 追踪像素、链接改写与 302、事件回传接口 | 3.7 |
| AnalyticsModule | 指标统计、看板、多任务合并报表、导出 | 3.6 / 3.8 |
| LeadModule | 评分模型（规则引擎）、意向客户筛选与导出 | 3.9 |
| OpenApiModule | 开放 API（OAuth2 client credentials + 限流） | 非功能·可集成性 |
| AuthModule | 用户认证、RBAC 权限、审计日志 | 非功能·安全性 |

### 4.2 发送队列与重试（核心）

使用 Redis + BullMQ 实现，满足文档 5 章"稳定性"要求：

- **队列设计**：
  - `mail:send-single`：单发邮件（优先级高，及时投递）；
  - `campaign:dispatch`：批量任务调度器，负责把任务拆分成单封投递任务（按速率分批入队）；
  - `mail:send-bulk`：批量单封发送（有速率限制，保护用户邮箱账号）；
  - `imap:fetch`：各绑定邮箱定时拉信（每账号独立任务）；
  - `event:flush`：追踪事件从 Redis 批量写入 PG。
- **重试策略**：指数退避（如 1min / 5min / 30min），重试次数按任务级可配置（默认 3 次）；
- **退信处理**：硬退（永久失败）立即标记并写入退信名单，避免重复发送；软退走重试；
- **速率控制**：按发件账号维度限速（BullMQ Rate Limiter），防止触发邮箱服务商限制导致封号；
- **幂等**：每封邮件携带唯一 `messageId`，重试前检查投递状态防止重复发送。

### 4.3 定时发送

- 任务级定时：BullMQ delayed job，到期由 `campaign:dispatch` 拆分入队；
- 修改/取消定时：删除未执行的 delayed job 即可，状态机保证一致性。

### 4.4 邮件收发协议适配

| 场景 | 方案 |
| --- | --- |
| 通用邮箱（企业邮箱/QQ/163 等） | Nodemailer（SMTP 发送）+ ImapFlow（IMAP 收信），预设主流服务商服务器参数模板 |
| Gmail | Gmail API + OAuth2（Gmail 已禁用基础密码认证，绑定必须走 OAuth 授权）；发送走 Gmail API，收信走 Gmail Push（Pub/Sub）或轮询 |
| Microsoft 365（预留） | Microsoft Graph API + OAuth2，接口层抽象 `MailProvider` 统一适配 |

**Provider 抽象**：定义统一接口（`send / fetch / markRead / getBounce`），SMTP-IMAP、Gmail API、ESP 各自实现，业务层无感切换。

### 4.5 追踪埋点（核心）

- **像素回传**：正文插入 `<img src="https://track.example.com/p.gif?e={eventId}">`，端点返回 1x1 GIF，事件写 Redis（`INCR` + `LPUSH`），由 `event:flush` 每 5 秒批量入库；
- **链接追踪**：发送前正则改写正文链接为 `https://track.example.com/c/{linkId}`，302 跳转到真实地址并记录点击事件；
- **回复归因**：IMAP 拉信时通过 `In-Reply-To` / `References` 头关联原 `messageId`，归因到任务收件人；
- **退信归因**：解析退信邮件（`multipart/report`、`delivery-status`），区分硬退/软退。

### 4.6 意向评分模型（规则引擎）

- 规则以 JSONB 存储于 `scoring_rules` 表，支持运营后台可配置；
- 初始规则维度（对应产品 3.9）：
  - 回复速度：`回复时间 = f(首次送达)`，越快分越高；
  - 关键词命中：回复正文命中正向词表（报价/试用/合作等），按词权重累加；
  - 互动频率：打开次数、点击次数、回复次数加权；
- 评分触发：事件入库后投递 `lead:score` 任务增量更新客户评分，避免全量重算；
- 规则结构示意：

```json
{
  "name": "默认评分模型",
  "rules": [
    { "type": "reply_speed",   "thresholds": [{ "maxHours": 1, "score": 30 }, { "maxHours": 24, "score": 15 }] },
    { "type": "keyword",       "keywords": [{ "word": "报价", "score": 25 }, { "word": "试用", "score": 20 }] },
    { "type": "open_count",    "perAction": 2, "maxScore": 10 },
    { "type": "click_count",   "perAction": 5, "maxScore": 20 }
  ],
  "hotLeadThreshold": 60
}
```

### 4.7 安全方案

| 项 | 方案 |
| --- | --- |
| 凭据加密 | SMTP/IMAP 密码、OAuth refresh token 用 AES-256-GCM 加密落库，密钥由 KMS 或环境变量管理，支持密钥轮换 |
| 传输安全 | 全站 TLS（HTTPS），SMTP/IMAP 强制 SSL/TLS |
| 认证 | JWT（Access + Refresh），密码 bcrypt |
| 权限 | RBAC（Casliber/Casbin）：管理员 / 运营 / 销售 / 只读，数据按团队隔离 |
| 审计 | 登录、绑定、发送、导出等敏感操作记录审计日志（who / when / what / ip） |
| 应用防护 | 全局参数校验（class-validator）、SQL 注入防护（ORM 参数化）、XSS（发送正文白名单过滤）、开放 API 限流 |

## 5. 数据层方案

### 5.1 存储选型分工

| 存储 | 用途 |
| --- | --- |
| PostgreSQL | 全部业务数据；`tracking_events`（追踪事件）按月分区 |
| Redis | BullMQ 队列、会话缓存、未读计数、热点看板缓存、追踪事件缓冲、分布式锁 |
| OSS / MinIO | 邮件附件、CSV/Excel 导出文件（签名 URL 下载） |
| ClickHouse（三期可选） | 事件量超过单机 PG 聚合能力后引入，承接多维报表；事件写入双发 |

### 5.2 核心数据模型（概要）

```
users / roles / audit_logs                 -- 权限与审计
mail_accounts                              -- 绑定邮箱（凭据加密字段、provider 类型、连接状态）
contacts                                   -- 联系人（与任务收件人互通）
conversations / messages                   -- 会话归档（messages 含 direction / status / in_reply_to）
campaigns                                  -- 邮件任务（状态机：draft→scheduled→sending→completed/failed/paused）
campaign_recipients                        -- 任务×收件人明细（status / open_count / click_count / last_event_at）
tracking_events                            -- 追踪事件（按月分区：type / occurred_at / link_id…）
scoring_rules / lead_scores                -- 评分规则与客户得分
templates / attachments / exports          -- 模板、附件、导出记录
```

**关键约束**：

- `campaign_recipients` 上唯一索引（campaign_id + recipient_email）保证不重复发送；
- `messages.external_message_id` 存储服务商 Message-ID，用于回复/退信归因；
- 退信名单以 `(mail_account_id, email)` 记录硬退状态，发送前校验拦截。

### 5.3 数据量与性能预估

| 表 | 增长预估 | 应对 |
| --- | --- | --- |
| tracking_events | 每万封约 3–5 万条（打开+点击） | 按月分区 + Redis 缓冲批量写；三期迁移 ClickHouse |
| messages | 与收发量线性 | 索引优化（account_id+received_at） |
| 看板聚合 | 多维查询 | 预聚合表（按天/任务/账号物化）+ Redis 缓存 5 分钟 |

## 6. API 设计约定

- 风格：RESTful，资源命名复数，统一响应结构 `{ code, message, data }`；
- 鉴权：`Authorization: Bearer <JWT>`；开放 API 走 OAuth2 client credentials；
- 分页：统一 `page / pageSize`，大列表用游标分页（收件箱、事件明细）；
- 文档：NestJS Swagger 自动生成 OpenAPI 3.0，作为开放 API 的交付物；
- 实时：`GET /api/events/subscribe`（SSE）推送任务进度、新邮件提醒。

## 8. 部署架构

### 8.1 一期（单机/小规模，≤1 万封/天）

Docker Compose 单机部署：

```
nginx (TLS + 静态资源)
  ├── api        (NestJS, 2 实例)
  ├── worker     (发送/拉信/评分, 按队列分组, 2–4 进程)
  ├── tracking   (轻量, 独立域名 track.example.com)
  ├── postgres   (主库, 每日备份)
  ├── redis      (AOF 持久化)
  └── minio      (附件存储)
```

### 8.2 二/三期扩展路径

- API 与 Worker 无状态化，容器编排迁移 K8s，Worker 按队列长度 HPA 扩容；
- PG 读写分离 + PgBouncer 连接池；
- 追踪服务独立扩容，事件写入切 ClickHouse；
- 多地域部署时对象存储就近接入。

## 9. 关键风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 用户自有邮箱直发送达率低、易被限流 | 批量任务失败率高 | 按账号限速 + 指数退避；提供 ESP 通道（阿里云邮件推送/SendGrid）作为可选增强；退信自动标记 |
| Gmail 无法走密码认证 | 绑定失败 | 一期即实现 Gmail OAuth2 授权绑定 |
| 追踪事件高并发写入 | 打开率高峰拖垮主库 | 像素端点只写 Redis，批量落库；独立域名与部署隔离 |
| 打开追踪因隐私代理（如 Apple MPP）失真 | 数据可信度 | 指标口径说明；以回复/点击等强信号为主做意向评分 |
| 凭据泄露 | 严重安全事故 | AES-256-GCM + KMS、审计日志、最小权限 RBAC |
| 邮件正文 XSS 注入 | 展示端风险 | 收件渲染沙箱 iframe + 内容白名单过滤 |

## 11. 备选方案说明（决策记录）

| 决策点 | 选择 | 备选 | 选择理由 |
| --- | --- | --- | --- |
| 后端语言 | Node.js + NestJS | Java Spring Boot | I/O 密集场景契合；前后端同语言、共享类型；交付效率优先。若团队为 Java 团队或需强事务/重型生态，可切 Spring Boot，架构不变 |
| 队列 | Redis + BullMQ | RabbitMQ | 定时任务、限速、重试 API 内置，运维成本低；规模大后可平滑替换 |
| 主库 | PostgreSQL | MySQL | JSONB 原生支持评分规则与灵活配置；分区表原生可用；分析函数更强 |
| 实时推送 | SSE | WebSocket | 进度推送为单向场景，SSE 更简单、断线自动重连 |
| 前端框架 | Vue 3 | React + Ant Design | 团队现状与组件生态匹配；二者均可，不构成架构约束 |
